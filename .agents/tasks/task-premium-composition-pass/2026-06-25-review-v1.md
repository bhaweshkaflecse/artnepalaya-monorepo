# Premium Cover Flow 3D carousel and vertical tightening pass

A composition-only change across LoginScreen and CreateScreen. LoginScreen gains deeper Cover Flow interpolation (more aggressive rotateY/scale/opacity curves), a new `translateX` overlap effect that slides neighbors toward center, and an animated `shadowOpacity` for iOS. The "Continue as Guest" link gets demoted visually (fontSize 12, opacity 0.75). CreateScreen reduces hero preview height from 32%/280px to 28%/240px and tightens vertical margins across the full layout (~40-50px recovered total).

**Watch for:** The `shadowOpacity` animated value is spread into styles via object spread rather than applied as a direct prop on `Animated.View`, which may silently fail to animate on some RN versions (**confirmed**). The `useNativeDriver: false` on the scroll event means all interpolation runs on the JS thread — with five simultaneous interpolations per visible item, this is a frame-budget risk on low-end Android (**likely**).

## High-level view

The carousel interpolation deepens every axis: scale drops from 0.65→0.6 at extremes, rotateY goes from ±18°→±25°, opacity from 0.3→0.25. A new `translateX` interpolation creates physical overlap between items. The transform array is reordered to place `perspective` first (correct for matrix composition). Adding a per-item animated `shadowOpacity` on iOS is the only structurally new interpolation — the rest are parameter tweaks. The concern here is the combination of five animated values per item with a JS-thread driver.

CreateScreen's changes are purely static style constants — no animated values, no logic changes. The hero area shrinks, spacing compresses, text inputs get shorter minimum heights. The risk is that `minHeight: 72` on the description textarea may feel cramped with a software keyboard visible on small screens (iPhone SE), but this is a design preference rather than a functional bug.

<summary>Issues (3)</summary>

1. **shadowOpacity spread may not animate** — The animated value is spread via `...(Platform.OS === 'ios' ? { shadowOpacity } : {})` into the style object. On some RN versions, spreading an `Animated.Value` into a plain object via conditional spread loses its animated binding. Verify on device that the shadow actually transitions smoothly; if it doesn't, move `shadowOpacity` to a direct style property rather than a spread conditional.

2. **Five JS-thread interpolations per visible item** — `useNativeDriver: false` means `scrollX` updates trigger JS-thread recomputations for `scale`, `rotateY`, `opacity`, `translateX`, and `shadowOpacity` for every rendered item on each frame. On low-end Android with 3-5 visible items, that's 15-25 interpolations per frame. Consider switching to `useNativeDriver: true` (which would require removing the conditional spread and applying shadow via `elevation` only) or using `react-native-reanimated` for native-threaded interpolation.

3. **CreateScreen textarea minHeight reduction on small screens** — `minHeight: 72` for the text area gives roughly 3 lines of visible text at fontSize 15 / lineHeight 22. On an iPhone SE (667pt height) with keyboard open, the remaining visible area must accommodate header, hero (240px), pagination, thumbnails, and the input field — tight but functional if a `KeyboardAvoidingView` or scroll-to-input behavior exists.

## Cover Flow shadow animation delivery

The `shadowOpacity` interpolation uses a 3-point input range (one step narrower than the 5-point range used by other properties). Items at index ±2 extrapolate — but `extrapolate: 'clamp'` caps them at 0.08. The delivery mechanism is the concern:

```tsx
...(Platform.OS === 'ios' ? { shadowOpacity } : {}),
```

React Native's `Animated.View` processes animated values in the style prop by traversing the style object and replacing `Animated.Value` instances with native node references. The object spread conditional creates a path where the animated value is merged into the main style object at render time. This *should* work because `Animated.View` traverses all style properties recursively. However, if the spread is evaluated before being passed to the native layer (e.g., in some style flattening implementations), the animated binding could be lost and the property would receive the raw numeric value at initial render time, then never update. This is confirmed as a potential issue by inspecting the code pattern — runtime verification on device is needed to determine if it manifests.

## JS-thread frame budget with useNativeDriver: false

```tsx
onScroll={Animated.event(
  [{ nativeEvent: { contentOffset: { x: scrollX } } }],
  { useNativeDriver: false }
)}
```

The native driver was likely disabled because `shadowOpacity` (an iOS layout property) cannot be animated via the native driver — it only supports `transform` and `opacity`. The consequence is that every scroll frame dispatches the offset to JS, which recalculates five interpolation outputs per rendered FlatList item. With FlatList default `windowSize`, the render window likely contains 5-7 items at ~58% screen width each plus 12px spacing.

On budget Android phones with slower JS engines, 25+ interpolation evaluations per frame at 60fps could cause frame drops during fast user-initiated scrolling. The auto-scroll timer (which uses `scrollToOffset`) produces fewer scroll events and is less affected. If `shadowOpacity` were dropped or made static, the entire animation could move to `useNativeDriver: true` and run entirely on the native thread.
