# Premium light-theme redesign for Login and CreateScreen

The LoginScreen moves from a dark overlay with AnimatedBackground to a white-canvas layout featuring a hero artwork carousel (auto-scrolling FlatList), animated branding section, statistics cards, and redesigned auth buttons. The CreateScreen replaces a basic functional layout with a premium upload experience: publish pill header, status banner, full-height hero preview with carousel navigation arrows, thumbnail strip, floating upload progress card, and a consolidated compliance section. Both screens preserve all business logic unchanged, with one exception: the publish button now fires through an animation callback that introduces a ~160ms delay and a double-tap race window.

**Watch for:** The CreateScreen's status badge shows "Media X/6" as the maximum but the actual enforcement still uses `MAX_IMAGES = 5` and `MAX_VIDEOS = 1` separately — the "6" is a UI label, not a unified cap, and could mislead users about what combinations are valid (confirmed). The placeholder carousel fetches images from `picsum.photos` on every mount, which will fail silently in offline/airplane mode and leave empty rounded cards (likely). The publish button animation wrapper opens a brief double-tap race window that didn't exist before (confirmed).

## High-level view

The LoginScreen's visual identity flipped from a dark immersive overlay to a bright, scrollable layout driven by a FlatList carousel and Animated API entries. The carousel auto-scrolls on a 4-second interval and falls back to picsum.photos placeholders when `authBackgroundMedia` is empty, introducing an external network dependency on the login screen's first-load experience.

The CreateScreen's media picker, FormData construction, validation, and publish pipeline are byte-for-byte unchanged. The primary risk lives in the status badge's "Media X/6" display which conflates the separate image and video caps into a single counter, and in the new `handlePublishPress` wrapper that adds an animation bounce before calling `handlePublish`.

The compliance section consolidates the previously separate AI disclosure, original content, and NSFW checkboxes into a single card with unchanged logic.

<summary>Issues (5)</summary>

1. **Status badge "Media X/6" misleads on valid combinations** — The badge suggests 6 total items are allowed, but the actual limit is 5 images + 1 video enforced independently. A user with 5 images sees "5/6" and expects to add another image when only a video slot remains. Display the split limits or match the badge to the actual logic.
2. **Placeholder carousel hits external network on every login mount** — `picsum.photos` URLs are hardcoded as fallback when `authBackgroundMedia` is empty. On poor connections this yields broken image cards with no loading state or error fallback. Use local bundled assets or add an `Image.onError` handler.
3. **AnimatedBackground component is now dead code** — The import was removed but the component file still exists. If no other screen uses it, it should be deleted to avoid confusion.
4. **Publish button animation adds ~160ms latency and double-tap race** — `handlePublishPress` runs a scale-down/up sequence (80ms + 80ms) and fires `handlePublish` in the completion callback. Under rapid double-taps, two publishes can fire before `isPublishing` flips to true. Add a local guard or disable the button immediately on first tap.
5. **Auto-scroll timer isn't gated by screen focus** — The LoginScreen's 4-second interval keeps firing even when the screen is unfocused (e.g., auth modal is open). Use `useIsFocused()` or `useFocusEffect` to pause the timer.

## Status badge vs actual media limits

The new CreateScreen adds a status badge displaying `Media {mediaItems.length}/6`:

```tsx
<View style={styles.statusBadge}>
  <Text style={styles.statusBadgeText}>Media {mediaItems.length}/6</Text>
</View>
```

The underlying `pickImage` logic enforces `MAX_IMAGES = 5` and `MAX_VIDEOS = 1` independently. A user who selects 5 images sees "5/6" and is told they can add one more — but that slot only accepts a video. Conversely, selecting 1 video first shows "1/6", implying 5 more of anything are allowed when in fact only 5 images are. The `selectionLimit` calculation (`Math.max(1, 6 - mediaItems.length)`) also uses the summed total, which is correct for the picker's `allowsMultipleSelection` but the per-type enforcement happens afterward and silently drops excess items via `Alert` + `continue`. The badge doesn't reflect this nuance.

The `limitsContainer` text still accurately says "Up to 5 images + 1 video", but the prominent badge contradicts it visually.

## Carousel fallback and offline behavior

When `authBackgroundMedia` is empty, the LoginScreen constructs:

```tsx
const placeholderMedia = [
  { url: 'https://picsum.photos/600/400?art=1', type: 'image' as const },
  { url: 'https://picsum.photos/600/400?art=2', type: 'image' as const },
  { url: 'https://picsum.photos/600/400?art=3', type: 'image' as const },
];
```

These are remote URLs hit on every app launch when the config API hasn't responded. There is no `onError` handler on the `<Image>` components, no loading placeholder, and no graceful fallback. On airplane mode the user sees three empty rounded rectangles (`backgroundColor: lightColors.surface`) which look broken rather than intentionally blank. The old `AnimatedBackground` component had built-in opacity transitions that hid loading states — the new approach trades that resilience for a carousel layout without matching the error handling.

## Publish button animation wrapper

The old CreateScreen wired the Publish button directly:

```tsx
<TouchableOpacity onPress={handlePublish} disabled={!canPublish}>
```

The new version introduces:

```tsx
const handlePublishPress = () => {
  Animated.sequence([
    Animated.timing(publishScaleAnim, { toValue: 0.92, duration: 80, useNativeDriver: true }),
    Animated.timing(publishScaleAnim, { toValue: 1, duration: 80, useNativeDriver: true }),
  ]).start(() => {
    handlePublish();
  });
};
```

`handlePublish` is only called in the animation's completion callback. If the user taps twice within 160ms, both taps start animation sequences, and both will eventually call `handlePublish`. The first call sets `isPublishing = true` which disables the button, but there's a race window where the second animation is already queued. The old code had no such window because `handlePublish` ran synchronously on tap.

## Auto-scroll timer lifecycle

```tsx
useEffect(() => {
  if (authBackgroundMedia.length <= 1) return;
  autoScrollTimer.current = setInterval(() => { ... }, 4000);
  return () => { clearInterval(autoScrollTimer.current); };
}, [authBackgroundMedia.length]);
```

This runs regardless of React Navigation focus state. If the user opens the Google OAuth webview, the interval keeps firing and calling `scrollToOffset` on a non-visible FlatList. Not a crash risk, but wastes resources and leaves the carousel at an unexpected position on return.

**Note on media pipeline audit (per user steering):** This diff does NOT change the media upload pipeline. The `pickImage` function, `handlePublish` FormData loop, `selectionLimit` calculation, and `formData.append('media', ...)` logic are byte-for-byte identical to the base commit. If media is being lost (user reports 4 images + 1 video selected but only 1 shows in Post Detail), the issue is NOT in this diff. The `PostDetailScreen` renders all `post.media` items via FlatList — if only 1 item shows, fewer items are being returned by the GET API. The problem likely lives in the backend multer configuration (field count limit or `maxCount` setting), the MongoDB storage layer, or an API serialization issue. This requires a backend investigation, not a frontend fix.
