# Production-blocking fixes: explore filters, feed freshness, tab crash, share page

This change fixes six production issues across the backend and mobile app. The explore category filter was broken because `artworkType` from form-data was stored as a literal JSON string instead of an array; it now gets the same parse treatment as `tags`. The recommendation engine guarantees fresh content by always including posts from the last 24 hours regardless of interest matching, and the feed cache TTL drops from 5 minutes to 1 minute. The Home tab crash is resolved by removing `getItemLayout` (which assumed fixed-height items). The share page gains an Android `intent://` deep link, a CSS scroll-snap gallery for multi-media posts, and the app.json gets notification icon configuration.

**Watch for:** The recommendation engine's `recentBoostPosts` array is never truncated to the page limit, so the `combined` array can exceed the requested page size (confirmed). The `hasNextPage` calculation still references the original `preferenceSlots`/`discoverySlots` rather than the adjusted remaining slots, making pagination unreliable when most posts are recent (confirmed). The notification icon is a full-color adaptive icon copied as a placeholder — Android requires monochrome/white-on-transparent for notification icons, so this will render as a solid square on most devices (confirmed).

## High-level view

The artworkType parsing fix in `createPost` and `updatePost` mirrors the existing tags pattern. The explore filter query doesn't need changing because MongoDB's `$regex` applies element-wise to array fields — the root cause was always the storage format, not the query. However, unlike tags, artworkType values are not case-normalized before storage, which creates a mismatch with the recommendation engine's exact-match `Set.has()` comparison.

The recommendation engine introduces a three-pool model: recent boost (last 24h), preference-matched, and discovery. Recent posts get unconditional inclusion and fill slots first, with preference and discovery sharing whatever remains. The design ensures new content surfaces immediately, but introduces a pagination bug: the `hasNextPage` check doesn't account for recent posts at all, and the combined result is never capped to the page limit.

The share page replaces the iframe-based Android deep link (which relied on a visibility-change race) with a direct `intent://` URI. The `intent://` scheme doesn't trigger Play Store fallback on all Android browsers (some fail silently on non-Chrome), but the explicit "Get on Google Play" button remains visible as a manual fallback.

1. **Feed page overflow** — `recentBoostPosts` is never sliced to `limit`, so `combined` can return more posts than the caller requested. Add `.slice(0, limit)` after combining, or cap `recentBoostPosts` before calculating remaining slots.
2. **Broken hasNextPage after recent-boost refactor** — `hasNextPage` compares `preferencePosts.length` against the original `preferenceSlots` (80% of limit), but preference/discovery pools are now smaller (they exclude all recent posts). 3. **Notification icon will render as solid square** — Android notification icons must be monochrome (white + transparent). The copied adaptive-icon.png is full-color and will appear as an opaque blob. Replace with a proper monochrome asset before shipping push notifications.
4. **Recent posts bypass popularity scoring** — Recent posts skip the `scorePost` step entirely, so a low-engagement post from 1 hour ago ranks above a viral post from 2 hours ago. Consider applying `scorePost` to `recentBoostPosts` or interleaving scored-recent with preference posts.
5. **artworkType case mismatch between storage and recommendation** — `createPost` does not normalize artworkType casing (unlike tags which get `.toLowerCase()`). The recommendation engine uses `interestSet.has(type)` (exact match). If user interests are stored as "Digital Art" but a post stores "digital art", the post won't match preferences and will only appear via the recent-boost or discovery pool.

## artworkType case sensitivity gap

Unlike `tags` which are normalized via `.map(t => t.toLowerCase().trim())`, the parsed `artworkTypeArray` is stored with whatever casing the client sends. The explore filter uses a case-insensitive regex, so queries work. But the recommendation engine's `interestSet.has(type)` is a case-sensitive exact match against the user's interest signals. If the mobile app sends `"Digital Art"` and the interest signals store `"digital art"` (or vice versa), the post won't match preferences — it falls into the discovery pool or relies on the 24-hour recent boost to surface.

## Recommendation engine: pagination and overflow

The three-pool split introduces two structural problems:

The `hasNextPage` check at line 189:

```js
const hasNextPage = preferencePosts.length > preferenceSlots || discoveryPosts.length > discoverySlots;
```

`preferenceSlots` is `Math.ceil(limit * weights.preferenceWeight)` — the original 80% of limit. But when recent posts consume most of the limit, `remainingPreferenceSlots` and `remainingDiscoverySlots` are much smaller. Since `preferencePosts` only contains non-recent posts (which are fewer after a busy day), it's unlikely to exceed the original `preferenceSlots`, making `hasNextPage` almost always false. The client would never request a second page.

Separately, `recentBoostPosts` is never truncated. If `candidatePosts` contains 30 recent posts and `limit` is 20, the function returns all 30 in `combined` because `remainingSlots` goes to 0 but the recent array itself isn't sliced. The calling code in `getFeed` passes this directly to the client, which would receive more items than it asked for. On a busy day this could mean returning 40+ posts in a single "page" of 20, causing memory pressure on mobile and defeating the purpose of pagination.

## Android intent:// fallback behavior

The `intent://` scheme is handled natively by Chrome on Android — if the app isn't installed and a `package` is specified, Chrome redirects to the Play Store. However, non-Chrome browsers (Samsung Internet, Firefox, Opera) may not implement the intent fallback spec. On those browsers, tapping "Open in App" when the app isn't installed produces no visible result. The retained "Get on Google Play" button below the intent link provides a manual escape path, but users may be confused by the silent failure of the primary CTA. This is a UX concern rather than a functional bug — it's an improvement over the previous iframe race in all cases. (likely)
