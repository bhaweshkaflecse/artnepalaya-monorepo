# Push notifications end-to-end, feed performance, and Nepal flag branding

Three independent features shipped in one diff: (1) backend `createNotification` now actually sends device pushes via Expo for Like/Save/Follow events, and the mobile client passes a `projectId` when requesting its push token; (2) the home feed FlatList gets `React.memo` on PostCard and virtualization tuning props, plus a video play-icon overlay; (3) a Nepal flag SVG asset is added and rendered on the login screen via `react-native-svg-transformer`.

Watch for: the `projectId` is hardcoded as the placeholder string `"YOUR_EAS_PROJECT_ID"` in `app.json`, so push token registration will fail in any EAS build until replaced (confirmed). The `React.memo` comparator only checks `post._id`, meaning mutable fields like `isLikedByMe` and `isSavedByMe` will not trigger re-renders when updated externally (confirmed). Push notification delivery adds two DB queries to every `createNotification` call on the hot path (confirmed).

## High-level view

Push notifications are wired by adding a `sendPushNotifications` call inside the existing `createNotification` service. The implementation fetches the recipient's push tokens and the sender's username, builds a type-specific title/body, and delegates to the Expo SDK. Failures are swallowed with a console log so the notification record is always returned. The mobile side adds the required `projectId` to `getExpoPushTokenAsync`, but that ID is a placeholder literal in the committed `app.json`.

Feed performance is addressed by memoizing PostCard and tuning FlatList windowing. The memo comparator is identity-based (`_id` equality), which is correct for feed scrolling but will suppress re-renders when like/save state mutates from outside the component.

The Nepal flag SVG is brought in through the standard `react-native-svg-transformer` pipeline with appropriate metro config and type declarations. No behavioral concerns in this feature.

<summary>Issues (5)</summary>

1. **Placeholder projectId will break push registration** — `app.json` ships `"YOUR_EAS_PROJECT_ID"` which will cause `getExpoPushTokenAsync` to fail or return an invalid token in EAS builds. Replace with the real project ID or read it from an environment variable at build time.
2. **Memo comparator ignores mutable post state** — `React.memo` on PostCard only compares `_id`. If the feed store updates `isLikedByMe`/`isSavedByMe` on an existing post object without changing its reference, the card won't re-render. Use shallow comparison or include the mutable fields.
3. **Two extra DB queries per notification on the hot path** — Every Like/Save/Follow triggers `User.findById` twice (recipient tokens + sender username) sequentially with the notification creation. Under high engagement this adds latency. Consider caching sender username from the request context or fetching tokens asynchronously after returning the notification.
4. **renderItem not memoized in HomeScreen** — `renderItem` is declared as an inline arrow function, which creates a new reference every render and partially defeats `React.memo` on PostCard. Wrap it in `useCallback`.
5. **No notification type fallback body** — If `type` is something other than Like/Save/Follow (e.g. a future Comment type), `body` falls through to `message || ''`, which may be empty. Consider a generic fallback body.

## Push delivery wired into createNotification

The backend change converts `createNotification` from a DB-only operation into a DB+push operation. After persisting the notification record, it fetches the recipient's `pushTokens` array and the sender's `username` in parallel, constructs a type-specific title/body, and calls `sendPushNotifications`. The push attempt is wrapped in a try/catch so a delivery failure never blocks the notification record from being returned to the caller.

The concern is performance on the hot path. Every Like or Save event now executes two additional `User.findById` queries (one projected to `pushTokens`, one to `username`) before returning. These queries are parallel with each other but sequential with the notification creation. Under burst engagement (many likes on a popular post), this doubles the DB load per event. A lightweight improvement: the sender username is almost always available in the request context that calls `createNotification`—passing it in the payload would eliminate one query per call.

## Placeholder projectId in app.json

The mobile client now passes `Constants?.expoConfig?.extra?.eas?.projectId` to `getExpoPushTokenAsync`. This is the correct pattern for Expo SDK 49+, but the value committed in `app.json` is the literal string `"YOUR_EAS_PROJECT_ID"`. In a development build this may still work (Expo falls back to the manifest), but in an EAS-built production binary it will produce an invalid or rejected token. This is a ship-blocker if the app is being released through EAS.

## React.memo comparator on PostCard

The comparator:

```tsx
export const PostCard = React.memo(PostCardComponent, (prevProps, nextProps) => {
  return prevProps.post._id === nextProps.post._id;
});
```

This returns `true` (skip re-render) whenever the post ID hasn't changed. But `isLikedByMe` and `isSavedByMe` are part of the post object and can change without the ID changing—for example, if the feed store merges updated post data after a background refresh. The component initializes `isLiked`/`isSaved` from `post.isLikedByMe` in `useState`, so stale props won't break local-only interactions (optimistic updates work via local state), but a feed refresh that returns updated like/save states will not propagate into already-rendered cards.

Additionally, `renderItem` in HomeScreen is not wrapped in `useCallback`, so it produces a new function reference on every render. FlatList's internals will still benefit from `React.memo` because it compares the item prop, but the optimization is incomplete.

## Notification type coverage gap

The push message builder handles Like, Save, and Follow, then falls through to a generic `title = 'New Notification'` with `body = message || ''`. If `message` wasn't supplied in the payload (it's optional in many call sites), the user receives a push with an empty body. Any future notification type added to the system will silently inherit this empty-body behavior until someone adds a case for it.
