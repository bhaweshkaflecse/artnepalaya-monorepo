# Push notifications, feed performance, and Nepal flag branding (v2)

Three features in one diff: backend push delivery wired into `createNotification` for Like/Save/Follow events, feed FlatList performance tuning with `React.memo` and virtualization props, and a Nepal flag SVG rendered on the login screen. All five concerns from the v1 review have been addressed — three via code fixes, two accepted as intentional trade-offs.

Watch for: repeated like/unlike cycles re-send push notifications each time since the coalescing logic resets the existing record and still fires delivery (likely). The `windowSize={5}` setting is aggressive and may cause visible blank frames on fast scroll for users with slower devices (possible).

## High-level view

Push delivery is fire-and-forget: the DB record is always returned regardless of whether the push succeeds. The coalescing logic (`findOneAndUpdate`) prevents duplicate notification records for repeated Like/Save on the same post, but a push is dispatched on every call — including when the notification already existed and was merely refreshed. A like/unlike/like cycle sends two device pushes for what the in-app list shows as one notification.

The feed memoization fixes from v1 are in place: the comparator now checks `_id`, `isLikedByMe`, and `isSavedByMe`, and `renderItem` is wrapped in `useCallback`. The FlatList windowing props (`windowSize={5}`) prioritize memory over scroll smoothness — this is tight for tall PostCards on lower-end devices.

## Push coalescing vs. delivery duplication

The `findOneAndUpdate` path for Like/Save reuses an existing notification record when user A likes post P again after an unlike — resetting `createdAt` and `isRead`. The push delivery block runs unconditionally after the DB operation, regardless of whether the notification was newly created or merely updated. The result: the post author's device buzzes again even though the notification list shows only one entry.

The fix is straightforward: track whether the notification was freshly created vs. updated, and only fire `sendPushNotifications` on fresh creation. The `findOneAndUpdate` call already provides this signal — if `existing` is truthy, the notification was updated rather than created.

```js
// Only send push for new notifications, not coalesced updates
const isNewNotification = !existing;
// ... later:
if (isNewNotification && recipient?.pushTokens?.length > 0) {
  await sendPushNotifications(recipient.pushTokens, title, body);
}
```

In a social art app, repeated like/unlike is uncommon, so the practical impact is low — but the asymmetry between the in-app list (one entry) and device pushes (multiple) is worth resolving.

## FlatList windowing trade-off

PostCard renders at a 4:5 aspect ratio plus header/actions (~85-90% of screen height per card). At `windowSize={5}`, only about 5-6 cards exist in memory at any time. On lower-end Android devices where the JS thread can't fill cells fast enough during fast scrolls, blank frames appear at the edges. Bumping `windowSize` to 7 would retain ~3 screens each direction and eliminate most visible blanks at minimal cost (2 extra PostCards in memory).
